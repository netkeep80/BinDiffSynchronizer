## Code review: текущие проблемы реализации

### ~~Проблема 1: Мёртвый код parse_object() в pjson_codec.h~~ ✅

**Решено в Этапе 8.1:** Удалена мёртвая `parse_object()` (~100 строк), `parse_object_v2()` переименована в `parse_object()`.

---

### ~~Проблема 2: Двойной парсинг объектов в parse_object()~~ ✅

**Решено в Этапе 9.4:** Функция `parse_object()` переписана для парсинга в один проход. Первый ключ-значение парсится напрямую во временный узел. Если объект оказывается `$ref`/`$base64` (ровно один ключ + строковое значение), временный узел извлекается и освобождается, целевой узел устанавливается в ref/binary. Для обычных объектов первый ключ-значение вставляется через `node_object_insert_id()` без повторного парсинга.

---

### ~~Проблема 3: Глобальное состояние в pam_pmm.h~~ (Этап A ✅)

**Решено (Этап A) в Этапе 10.1:** Три разрозненные статические переменные (`filename`, `root_offset`, `initialized`) инкапсулированы в структуру `pam_pmm_state` с методом `reset()`. Глобальный синглтон `pam_pmm_global_state()` заменяет прямой доступ к переменным. Функции `detail::` делегируют синглтону для обратной совместимости. Добавлены 4 теста.

### ~~Проблема 4: Утечка временных узлов метрик~~ ✅

**Решено в Этапе 8.4:** Pre-allocated один именованный узел `pjson_db_pmm.metrics_tmp` при создании БД.
Все вызовы `_get_metrics()` переиспользуют этот узел вместо аллокации нового.
Добавлены 3 теста: проверка отсутствия роста slot_count, переиспользования node_id, корректности значений.

---

### ~~Проблема 5: Неэффективное побайтовое копирование binary в node_clone()~~ ✅

**Решено в Этапе 9.1:** Побайтовое копирование заменено на bulk-метод: данные копируются в промежуточный `std::vector<uint8_t>`, затем `parray::resize()` + `memcpy`. Вместо O(N) переразрешений PMM-указателей — однократная аллокация и одно копирование. Добавлены 4 теста.

---

### ~~Проблема 6: Неэффективное создание + удаление временных слотов в node_clone()~~ ✅

**Решено в Этапе 9.2:** Добавлены функции `node_array_push_back_id()` и `node_object_insert_id()` для прямой вставки существующего node_id в массив/объект без создания временного слота. `node_clone()` переписан с использованием этих функций. Удалено создание и удаление временных null-слотов, что вдвое сокращает количество аллокаций/деаллокаций при клонировании. Добавлены 7 тестов.

---

### ~~Проблема 7: Отсутствие escaping '/' в path-сегментах~~ ✅

**Решено в Этапе 10.2:** Реализована поддержка RFC 6901 (JSON Pointer) для путей. Добавлена функция `pjson_decode_rfc6901_segment()` в `pjson_db_helpers.h`, которая декодирует `~1` → `/` и `~0` → `~`. Декодирование применяется в `_walk_path()` и `pjson_split_path()`. Ключи, содержащие `/` и `~`, теперь доступны через path-адресацию с экранированием. Добавлены 17 тестов.

---

### ~~Проблема 8: Hardcoded максимальная глубина $ref~~ ✅

**Решено в Этапе 8.2:** Магическое число `32` вынесено в именованную константу `PJSON_MAX_REF_DEPTH` с документацией. Константа используется в `node_view::deref()` и `pjson_db_pmm::resolve_ref()`.

---

### ~~Проблема 9: Дублирование обхода поддерева (array/object) в _free_node_tree и _resolve_refs_in_subtree~~ ✅

**Решено в Этапе 9.3:** Добавлена функция `pjson_traverse_subtree_postorder()` для post-order обхода (дети → родитель).
`_free_node_tree()` переписан через `pjson_traverse_subtree_postorder()` с visitor `pjson_free_node_visitor` (в `pjson_db_helpers.h`).
`_resolve_refs_in_subtree()` переписан через `pjson_traverse_subtree()` с visitor `_resolve_refs_visitor` (в `pjson_db_pmm.h`).
Дублирование рекурсивного обхода array/object устранено.

---

### ~~Проблема 10: node_view::tag() вызывает _resolve() при каждой проверке is_*()~~ ✅

**Решено в Этапе 10.3:** Оптимизированы горячие пути для сокращения избыточных вызовов `pmm_resolve<node>()`:

1. **`is_number()`** — переписан с единственным вызовом `tag()` вместо трёх (через `is_integer()`, `is_uinteger()`, `is_real()`).
2. **`is_null()`** — убрана избыточная проверка `is_error()` (уже обрабатывается внутри `tag()`).
3. **`deref()`** — единственный `pmm_resolve` за итерацию вместо отдельных `is_ref()` + `ref_target()`.
4. **`pjson_traverse_subtree` / `pjson_traverse_subtree_postorder`** — единственный `tag()` вместо цепочки `is_array()` + `is_object()`.
5. **`pjson_free_node_visitor`** — используется `n->tag` напрямую вместо повторного `v.tag()`.
6. **`pjson_count_visitor`** — единственный `pmm_resolve` для получения тега и данных.
7. **`_walk_path()`** — единственный `tag()` вместо цепочки `is_object()` + `is_array()`.
8. **`erase()`** — единственный `tag()` вместо цепочки `is_object()` + `is_array()`.

Добавлены 14 тестов.

### Проблема 11: Отсутствие const-корректности в _walk_path

**Файл:** `pjson_db_pmm.h`, строка 593

Метод `_walk_path<bool>()` объявлен `const`, но в режиме `CreateMode=true` модифицирует дерево узлов. Это возможно только потому, что PMM — глобальное состояние, и модификация происходит через глобальные функции, а не через членов класса.

**Связь:** Это следствие Проблемы 3 (глобальное состояние).

---

### ~~Проблема 12: Нет валидации UTF-8 codepoints > 0x10FFFF в парсере~~ ✅

**Решено в Этапе 8.3:** Функция `encode_utf8()` теперь возвращает `bool` и отклоняет codepoints > 0x10FFFF и одиночные суррогаты (0xD800–0xDFFF). Вызовы в `parse_string()` проверяют возвращаемое значение и возвращают `false` при невалидных кодовых точках.

## Анализ: pvector vs parray для JSON array (Этап 8.4, Issue #188)

### Характеристики

| Критерий | parray (текущий) | pvector |
|----------|-----------------|---------|
| Структура данных | Динамический массив (аналог std::vector) | AVL order-statistic дерево |
| Доступ по индексу | O(1) | O(log n) |
| push_back | Амортизированный O(1) | O(log n) |
| pop_back | O(1) | O(log n) |
| insert(i) | O(n) — memmove | Не поддерживается (только push_back) |
| erase(i) | O(n) — memmove | O(log n) |
| Итераторы | Нет (raw pointer) | Есть (AvlInorderIterator) |
| Кэш-локальность | Отличная (контигуозная память) | Плохая (разрозненные узлы) |
| Overhead на элемент | Минимальный (только данные) | Значительный (TreeNode: weight, left, right, parent, height) |
| Overhead на массив | 3 поля (size, capacity, data_idx) | 1 поле (root_idx) |

### Вывод

**parray — правильный выбор** для JSON-массивов по следующим причинам:

1. **Доступ по индексу O(1)** — критично для JSON (парсинг, сериализация, навигация по path вида `/arr/0/field`).
2. **Амортизированный O(1) push_back** — основная операция при построении массивов из JSON.
3. **Кэш-локальность** — контигуозное хранение элементов быстрее на реальном hardware при итерации.
4. **Низкий overhead** — JSON-документы часто содержат множество мелких массивов; parray экономит память.
5. **Типичный JSON-паттерн** — массивы строятся при парсинге (append) и читаются (index access); insert/erase в середину редки.

pvector был бы предпочтительнее **только** при частых удалениях из середины больших массивов (O(log n) vs O(n)), но это нетипично для JSON.

**Замечание:** Комментарии в `pjson_node.h` (node_tag::binary и node_tag::array) ошибочно указывали `pvector` вместо `parray` — исправлено.
